# Foxi Bot — Подход 1: Внешняя AI-модель + кнопка телефона + самообучение

Дата: 2026-09-11
Статус: утверждённый дизайн (выбран Подход 1 — минимальная интеграция внешней модели)

## Суть подхода

Внешняя «умная» модель становится основным провайдером (`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`), текущая бесплатная Llama 3.3 70B уходит в `LLM_FALLBACKS` как запасной вариант. Кнопка «Поделиться номером» добавляется в начало диалога, телефон связывает чат с карточкой CRM, но агент спрашивает имя ребёнка перед показом персональных данных. Самообучение работает автоматически: ночной анализ → автоприменение изменений → лог + кнопка отката в админке.

---

## 1. Архитектура провайдеров LLM

**Текущее состояние:** бот использует OpenRouter с бесплатной Llama 3.3 70B как основной провайдер, каскад поддерживает fallback через `LLM_FALLBACKS`.

**Что меняется:**

- Внешняя «умная» модель (credentials от заказчика) становится основным провайдером.
- Llama 3.3 70B переезжает в fallback — подхватывает диалог, если основная недоступна.
- `LLM_PII_REDACTION=true` остаётся включённой: имена, телефоны, даты рождения заменяются на `[NAME_1]`, `[PHONE_1]`, `[DATE_1]` перед отправкой в стороннюю модель, восстанавливаются после получения ответа.

**Конфигурация (.env):**

```env
LLM_BASE_URL=<base_url_провайдера>
LLM_API_KEY=<ключ>
LLM_MODEL=<название_модели>
LLM_FALLBACKS=[{"base_url":"https://openrouter.ai/api/v1","api_key":"<текущий_ключ>","model":"meta-llama/llama-3.3-70b-instruct:free"}]
LLM_PII_REDACTION=true
```

**Что это даёт:**

- Родители получают ответы от топовой модели.
- Если провайдер упал, бот автоматически переключается на бесплатный и продолжает работать.
- ПДн защищены: сторонний провайдер видит только плейсхолдеры, не реальные данные.

## 2. Кнопка «Поделиться номером» и идентификация

**Текущий поток:** новый пользователь пишет боту → приветствие → диалог → при записи бот запрашивает телефон текстом.

**Новый поток:**

1. Пользователь открывает бота → приветствие + кнопка **📞 Поделиться номером** (Telegram `request_contact=True`, аналог в MAX).
2. Пользователь жмёт кнопку → телефон приходит как `message.contact.phone_number`.
3. Бот нормализует телефон (последние 10 цифр), вызывает `bb_store.find_student_by_phone(phone)`.
4. Варианты:
   - **Не нашёл:** телефон сохраняется в `conv.lead.phone`, CRM-карточка не подтягивается. Бот продолжает как с новым лидом.
   - **Нашёл одного:** бот видит ФИО ребёнка из CRM, но не показывает персональные данные сразу. Спрашивает: «Как зовут вашего ребёнка?» Если ответ совпадает с ФИО из карточки (нечёткое сравнение: «Маша» = «Мария», «Саша» = «Александра») → идентификация завершена, карточка активна. Если не совпадает → бот работает как с новым лидом.
   - **Нашёл нескольких** (один телефон → два ребёнка в CRM): бот спрашивает: «У вас в школе занимается несколько детей. Про кого из них вопрос: Маша (7 лет) или Петя (10 лет)?» Родитель выбирает → идентификация завершена для выбранного ребёнка.
5. Если пользователь **не нажал кнопку**: бот не отвечает на вопросы по сути, только повторяет: «Чтобы я мог вам помочь, поделитесь, пожалуйста, номером телефона через кнопку ниже 👇».

**Технические детали:**

- Telegram: `ReplyKeyboardMarkup` с `KeyboardButton(text="📞 Поделиться номером", request_contact=True)`.
- MAX: аналогичный механизм через кнопку контакта (проверить API-документацию).
- Обработка `message.contact` добавляется в `telegram_client.py` / `max_client.py`.
- Логика идентификации — новая функция `identify_customer(phone, user_input_name)` в `app/sales.py` или `app/crm_ingest.py`.

## 3. Обновлённый системный промпт

**Тон:** вежливое «вы», тёплый премиальный стиль, эмодзи по делу (не в каждом сообщении). Как консультант дорогой школы, а не менеджер масс-маркета.

**Длина ответов:** 2–4 предложения. Если тема большая — разбить на несколько сообщений подряд. Форматирование: заголовки жирным (`**Заголовок**`), абзацы, списки, разделители.

**Ключевые изменения:**

- Убрать фразу про «Фокси — лис мужского рода» (это было для голосового ассистента, здесь неактуально).
- Добавить инструкцию: «Ты консультируешь только идентифицированных родителей. Если человек не поделился телефоном, вежливо попроси его сделать это через кнопку и не отвечай на вопросы по сути».
- Добавить: «Когда родитель идентифицирован, ты видишь информацию о его ребёнке из CRM: группу, расписание, посещаемость, домашние задания, успеваемость. Используй эту информацию, чтобы отвечать конкретно и персонально».
- Уточнить границы: «Ты НЕ консультируешь по финансам: балансу, задолженностям, возвратам — это вопросы к администратору школы».

**Новый раздел — форматирование:**

- 2–4 предложения на сообщение; если тема требует больше — несколько сообщений подряд по смысловым блокам.
- `**жирный текст**` для ключевых слов и заголовков.
- Списки — через дефис или нумерацию, каждый пункт с новой строки.
- Эмодзи только там, где усиливают смысл: 📅 для дат, ✅ для подтверждений, 📞 для контактов. Не в конце каждого предложения.

## 4. Интеграция с CRM для консультаций

**Что агент видит после идентификации:**

- `bb_store.find_student_by_phone()` → `student_id`.
- Через `bigben_v2.student(student_id)`: ФИО ребёнка, возраст, группа, педагог группы.
- Через `bigben_v2.lessons(date_from, date_to)` (фильтр по `student_id`): расписание на неделю вперёд, история посещаемости (присутствовал / отсутствовал / опоздал).
- Домашние задания и оценки/комментарии педагога — через внутренние таблицы CRM (уточнить наличие endpoint в BigBen API).

**Что агент НЕ видит:**

- Баланс, задолженности, платежи, счета.
- Данные других детей этого родителя, пока родитель явно не попросит переключиться.

**Примеры использования:**

- «Когда у нас следующее занятие?» → «Следующее занятие у Маши — в среду, 12 марта, в 17:00. Группа Elementary A2, преподаватель Анна Петровна».
- «Как Маша занимается?» → «Маша посетила 8 из 10 последних занятий, пропустила только две по болезни. Педагог отмечает отличное участие в диалогах и старательность в домашних заданиях».

**Технические детали:**

- Новая функция `get_customer_context(student_id)` в `app/crm_store.py` или `app/bb_store.py`.
- Вызывается после успешной идентификации, результат добавляется в системный промпт как `{customer_context}`.
- Промпт: «Информация о ребёнке родителя:\n{customer_context}».

## 5. Самообучение 24/7 с автоприменением и откатом

**Уже реализовано:**

1. Логирование пробелов в знаниях — `app/insights.py`.
2. Оценка ответов перед отправкой — `app/critic.py`.
3. Долгосрочная память — `app/recall.py` (сжатие старых диалогов в дайджесты).

### 5.1. Ночной анализатор (новый модуль `app/learning_loop.py`)

Cron-задача каждую ночь в 03:00:

1. **Читает логи за последние 24 часа:**
   - таблица `insights` → вопросы без уверенного ответа;
   - таблица `messages` + critic → забракованные / низко оценённые ответы;
   - таблица `events` → повторяющиеся вопросы (3+ разных родителей за день).
2. **Генерирует улучшения через LLM (роль `ROLE_CRITIC`):**
   - Промпт: «Вот 5 вопросов, на которые бот ответил слабо [примеры]. Вот текущий системный промпт [текст]. Предложи конкретные изменения: что добавить в базу знаний, что уточнить в инструкциях».
   - LLM возвращает структурированный JSON:

```json
{
  "kb_additions": [
    {"topic": "Перенос занятий", "text": "Если родитель пропустил занятие по уважительной причине (болезнь, справка), он может перенести его на другой день той же недели, согласовав с администратором. Переносы по личным причинам — только для абонементов Premium."}
  ],
  "prompt_changes": [
    {"section": "Как отвечать", "change": "add", "text": "Если родитель спрашивает про перенос, уточни причину пропуска — от этого зависит возможность переноса."}
  ]
}
```

3. **Применяет изменения автоматически:**
   - Обновления базы знаний → новые записи в `knowledge_base` (или дописывает в `app/knowledge/kb_dynamic.py`, если таблицы нет).
   - Изменения промпта → `crm_store.prompt_add(new_version, metadata={"source": "learning_loop", "changes": [...]})` + `prompt_activate(new_version_id)`.
   - Логирование в новую таблицу:

```sql
CREATE TABLE learning_log (
  id INTEGER PRIMARY KEY,
  applied_at TIMESTAMP,
  prompt_version_before INTEGER,
  prompt_version_after INTEGER,
  changes_json TEXT,          -- diff в JSON
  insights_analyzed INTEGER,  -- сколько записей из insights обработано
  status TEXT DEFAULT 'active'  -- active | rolled_back
);
```

4. **Отчёт администратору** (опционально, если есть Telegram ID админа): «Ночной анализ завершён. Применено 3 улучшения: добавлено 1 правило в базу знаний, уточнены 2 инструкции в промпте. Подробности: /admin/learning_log».

### 5.2. Интерфейс отката (новый эндпоинт `/admin/learning_log`)

- Таблица всех применённых изменений: дата/время, версия промпта до/после, diff (было/стало), статус (active / rolled_back).
- Кнопка «Откатить» возле каждой записи:
  - вызывает `crm_store.prompt_activate(prompt_version_before)`;
  - меняет `status` записи на `rolled_back`;
  - логирует откат как новую запись в той же таблице.

**Что это даёт:** бот улучшается сам, без участия администратора; ошибочное изменение откатывается одной кнопкой; история всех изменений сохраняется.

## 6. Изменение формы регистрации

**Текущий поток:** `registration.py` — fio_parent → fio_child → birthday → phone (парсинг из текста).

**Новый поток:**

- Если телефон уже есть (пришёл через кнопку `request_contact`) → форма начинается сразу с `fio_parent`, шаг `phone` пропускается.
- Если телефона нет → форма работает как сейчас.

**Технические детали:**

- В `app/memory.py` класс `Lead` уже имеет поле `phone`.
- В `registration.py` функция `handle_registration()` проверяет `conv.lead.phone is not None` → шаг `phone` пропускается.
- Форма собирает только недостающие данные, затем отправляет в `bigben.create_lead()`.

## 7. Обработка недоступности внешней модели

1. `app/llm.py` делает 3 попытки с экспоненциальной паузой (0.25s → 0.5s → 1s).
2. Если все попытки упали → каскад переходит к следующему провайдеру из `LLM_FALLBACKS`.
3. Llama 3.3 70B (запасной) отвечает на вопрос родителя.
4. В логах: `logger.error("LLM cascade exhausted primary provider, switched to fallback")`.
5. Родитель не видит разницы — ответ приходит чуть медленнее (в пределах `LLM_TOTAL_BUDGET_SEC=45s`).

**Мониторинг:**

- Эндпоинт `/health` уже показывает статистику провайдеров: `llm_gateway.stats()`.
- Добавить счётчик переключений на fallback: `"fallback_switches": N`.
- Рост счётчика = основной провайдер нестабилен.

## Что НЕ входит в этот дизайн

- Голосовые сообщения и распознавание речи (бот текстовый).
- Webhook-уведомления из CRM о новых событиях (отдельная фича).
- A/B-тестирование промптов.
- Ручное редактирование промпта в админке (версии создаются только через learning loop или миграции).

## План внедрения (чек-лист)

1. `.env` / `app/config.py`: внешняя модель — основной провайдер, Llama 3.3 70B — в `LLM_FALLBACKS`.
2. `telegram_client.py` / `max_client.py`: кнопка «📞 Поделиться номером» + обработка `message.contact`.
3. `app/sales.py`: `identify_customer()` — поиск по телефону, подтверждение имени ребёнка, выбор при нескольких детях.
4. `app/crm_store.py` / `app/bb_store.py`: `get_customer_context(student_id)` + вставка в системный промпт.
5. Системный промпт: новый тон, правила идентификации, форматирование, границы (без финансов).
6. `app/registration.py`: пропуск шага `phone`, если телефон уже известен.
7. `app/learning_loop.py`: ночной анализатор (cron 03:00) + таблица `learning_log`.
8. Админка: эндпоинт `/admin/learning_log` с diff и кнопкой отката.
9. `/health`: счётчик `fallback_switches`.
