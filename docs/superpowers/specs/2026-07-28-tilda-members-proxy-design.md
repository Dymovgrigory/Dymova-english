# Личный кабинет остаётся на Tilda после переезда домена — дизайн

**Дата:** 2026-07-28
**Статус:** утверждён владельцем, реализуется.

**Ревизия (тот же день, после первой попытки деплоя):** исходный вариант (прозрачный reverse_proxy Caddy → Tilda) не прошёл верификацию — DDoS-Guard перед Tilda блокирует запросы с IP этого сервера (датацентр Yandex Cloud) кодом 425 независимо от реального посетителя за прокси. Заменено на HTTP-редирект на отдельный поддомен, у которого DNS указывает прямо на Tilda — подробности ниже, разделы «Архитектура» и «Caddy-конфигурация» обновлены под новый подход.

## Контекст

Домен `dymova-english.ru` уже переезжал с Tilda на собственный сервер (Yandex Cloud VM, `89.169.132.104`, Caddy) в Сессии 30 (`DEVLOG.md`). После переезда ссылка «Личный кабинет» (`https://dymova-english.ru/members/login`, PR #107) стала отдавать 404 — это встроенная фича Tilda (Tilda Members), которая существует только на хостинге Tilda и была потеряна при переключении DNS.

Владелец в моменте вручную вернул A-запись домена обратно на Tilda (`176.57.67.189`), чтобы кабинет снова заработал — это временный откат, не финальное состояние.

**Цель этого захода:** довести миграцию с Tilda до конца (домен снова отдаётся с собственного сервера), но сохранить работающий личный кабинет Tilda на том же домене — до тех пор, пока не появится собственная реализация личного кабинета (вне рамок этой задачи).

## Из чего явно исключено

- Реализация собственного личного кабинета взамен Tilda — отдельная будущая задача, не здесь.
- Перенос кабинета на поддомен (`lk.dymova-english.ru` и т.п.) — рассмотрено и отклонено владельцем в пользу прозрачного проксирования на том же домене, чтобы не трогать существующие ссылки в шапке/подвале сайта.
- Прочие Tilda-зависимости (формы заявок, лента `/news`) уже мигрированы в предыдущих сессиях (27, 25) и этой задачи не касаются.

## Архитектура

- DNS A-записи `dymova-english.ru` и `www.dymova-english.ru` возвращаются на `89.169.132.104` (собственный сервер, тот же что уже отдаёт `new.dymova-english.ru` и бота).
- Новый поддомен `tilda-members.dymova-english.ru` — DNS указывает прямо на Tilda (`176.57.67.189`), **не** на собственный сервер. Добавлен как разрешённый домен/алиас в настройках проекта 2053071 в личном кабинете Tilda (иначе Tilda не будет знать, каким сайтом отвечать на этот hostname) — это делает владелец вручную, доступа туда у агента нет.
- В Caddy, в существующем блоке `dymova-english.ru, www.dymova-english.ru { ... }` (`bot/deploy/Caddyfile`), добавляется правило `handle /members/*`, которое отдаёт HTTP 302 редирект на `https://tilda-members.dymova-english.ru{исходный путь}`. Все остальные пути обслуживаются статикой как раньше.
- Браузер посетителя при переходе по `https://dymova-english.ru/members/login` получает редирект и сам, напрямую (своим обычным IP, не через наш сервер), подключается к Tilda за страницей входа.

## Почему не прямое проксирование (отклонённый вариант)

Первая версия дизайна использовала `reverse_proxy` (Caddy сам, как клиент, обращался к Tilda). При проверке (см. план, Task 3) обнаружилось: DDoS-Guard перед Tilda возвращает `HTTP 425` с телом `D'oh!` (плоская блокировка, не решаемый JS-challenge) на любой запрос, пришедший с IP этого сервера (Yandex Cloud, датацентр) — контрольный запрос с обычного (не датацентрового) IP в то же время проходил чисто, `200 OK`. Поскольку при reverse-proxy все посетители выглядели бы для Tilda одинаково — с IP нашего сервера, — это сломало бы кабинет для всех одинаково, а не только для ботов. Редирект избегает этого класса проблем полностью: Tilda всегда видит реальный IP реального браузера.

## DNS-записи

- `tilda-members.dymova-english.ru → 176.57.67.189` (текущий IP Tilda для проекта 2053071) — целевой домен редиректа.
- IP Tilda для этого проекта уже менялся один раз без действий владельца (было `185.215.4.12`, стало `176.57.67.189`). При повторной смене — правится одна эта DNS-запись в кабинете reg.ru, без изменений в Caddyfile и без передеплоя.

## Caddy-конфигурация (суть, не финальный код — уточняется в плане реализации)

```
dymova-english.ru, www.dymova-english.ru {
    handle /members/* {
        redir https://tilda-members.dymova-english.ru{uri} 302
    }
    root * /srv/foxinburg-site
    try_files {path} {path}/index.html
    file_server
}
```

- `handle` (не `handle_path`) сохраняет исходный путь в `{uri}`, так что `/members/login` редиректит на `https://tilda-members.dymova-english.ru/members/login`, а не теряет суффикс.
- `302` (временный редирект) — не `301`, чтобы не закреплять permanent-редирект в кэшах браузеров/поисковиков на случай, если позже появится собственный кабинет и путь снова станет обслуживаться с основного домена.

## Риски и ограничения

1. **Сертификат Tilda для `tilda-members.dymova-english.ru` (и вообще для проекта) может перестать продлеваться так же надёжно, как раньше** — тот же класс риска, что и с исходным доменом ранее: Let's Encrypt на стороне Tilda обычно продлевает сертификат через проверку владения доменом. Пока `tilda-members.dymova-english.ru` весь срок указывает прямо на Tilda (не на наш сервер), проверка домена должна проходить нормально — риска здесь меньше, чем в отклонённом варианте с reverse_proxy, но стоит перепроверить `/members/login` в живую в рамках обычного мониторинга сайта.
2. **Смена URL в адресной строке браузера** на короткое время при входе/навигации внутри кабинета (`tilda-members.dymova-english.ru` вместо `dymova-english.ru`) — сознательный компромисс ради надёжности; не влияет на SEO (страница `noindex`) и не ломает функциональность, только визуально заметно.
3. **Личный кабинет перестанет работать, если владелец забудет добавить `tilda-members.dymova-english.ru` в список доменов проекта в кабинете Tilda** — без этого шага Tilda не будет знать, каким проектом отвечать на этот hostname. Проверяется прямым curl-тестом на этапе верификации (см. план) — не гадаем, а реально проверяем перед тем как трогать боевой DNS.

## Проверка после деплоя

- Сначала — до переключения основного DNS: `curl` на `tilda-members.dymova-english.ru/members/login` напрямую — ожидается 200 и разметка Tilda Members. Отдельно — `curl -i` на `dymova-english.ru/members/login` через IP нового сервера (`--resolve`) — ожидается `302` с `Location: https://tilda-members.dymova-english.ru/members/login`.
- После переключения основного DNS: то же самое, но уже на реальном `dymova-english.ru`, без `--resolve`.
- Живой тест в браузере: открыть `https://dymova-english.ru/members/login`, дойти до формы входа на `tilda-members.dymova-english.ru`, залогиниться существующим аккаунтом, убедиться что сессия/куки работают.
- Проверить, что остальной сайт (статика, `/api/lead`, обычные страницы) не задет изменением.
