# Личный кабинет остаётся на Tilda после переезда домена — дизайн

**Дата:** 2026-07-28
**Статус:** утверждён владельцем, готов к планированию реализации.

## Контекст

Домен `dymova-english.ru` уже переезжал с Tilda на собственный сервер (Yandex Cloud VM, `89.169.132.104`, Caddy) в Сессии 30 (`DEVLOG.md`). После переезда ссылка «Личный кабинет» (`https://dymova-english.ru/members/login`, PR #107) стала отдавать 404 — это встроенная фича Tilda (Tilda Members), которая существует только на хостинге Tilda и была потеряна при переключении DNS.

Владелец в моменте вручную вернул A-запись домена обратно на Tilda (`176.57.67.189`), чтобы кабинет снова заработал — это временный откат, не финальное состояние.

**Цель этого захода:** довести миграцию с Tilda до конца (домен снова отдаётся с собственного сервера), но сохранить работающий личный кабинет Tilda на том же домене — до тех пор, пока не появится собственная реализация личного кабинета (вне рамок этой задачи).

## Из чего явно исключено

- Реализация собственного личного кабинета взамен Tilda — отдельная будущая задача, не здесь.
- Перенос кабинета на поддомен (`lk.dymova-english.ru` и т.п.) — рассмотрено и отклонено владельцем в пользу прозрачного проксирования на том же домене, чтобы не трогать существующие ссылки в шапке/подвале сайта.
- Прочие Tilda-зависимости (формы заявок, лента `/news`) уже мигрированы в предыдущих сессиях (27, 25) и этой задачи не касаются.

## Архитектура

- DNS A-записи `dymova-english.ru` и `www.dymova-english.ru` возвращаются на `89.169.132.104` (собственный сервер, тот же что уже отдаёт `new.dymova-english.ru` и бота).
- В Caddy, в существующем блоке `dymova-english.ru, www.dymova-english.ru { ... }` (`bot/deploy/Caddyfile`), добавляется правило `handle_path /members/*`, которое перехватывает эти запросы **до** `file_server` и проксирует их на Tilda. Все остальные пути обслуживаются статикой как сейчас.
- Со стороны посетителя ничего не меняется: ссылка `https://dymova-english.ru/members/login` в шапке/подвале сайта остаётся как есть.

## DNS-индикатор для Tilda-апстрима

- Новая A-запись `tilda-origin.dymova-english.ru → 176.57.67.189` (текущий IP Tilda для проекта 2053071). Используется только как имя апстрима в Caddy — самостоятельного сайт-блока для неё нет.
- IP Tilda для этого домена уже менялся один раз без действий владельца (было `185.215.4.12`, стало `176.57.67.189`). При повторной смене — правится одна DNS-запись в кабинете reg.ru, без изменений в Caddyfile и без передеплоя.

## Caddy-конфигурация (суть, не финальный код — уточняется в плане реализации)

```
dymova-english.ru, www.dymova-english.ru {
    handle_path /members/* {
        reverse_proxy https://tilda-origin.dymova-english.ru:443 {
            transport http {
                tls_server_name dymova-english.ru
            }
        }
    }
    root * /srv/foxinburg-site
    try_files {path} {path}/index.html
    file_server
}
```

- `tls_server_name dymova-english.ru` — явно задаёт SNI при TLS-подключении к Tilda, чтобы её edge (за DDoS-Guard) узнал нужный проект по домену, а не по имени апстрима.
- Host-заголовок к апстриму не переопределяется — Caddy по умолчанию пробрасывает исходный `Host: dymova-english.ru`, что и требуется Tilda для маршрутизации на нужный проект.

## Риски и ограничения

1. **Сертификат Tilda для `dymova-english.ru` может перестать продлеваться.** Let's Encrypt на стороне Tilda обычно продлевает сертификат через проверку, что домен указывает на инфраструктуру Tilda — а после этого изменения он больше не указывает. Текущий сертификат живой (выпущен 26.07.2026, истекает 24.10.2026). Митигация: зафиксировать в `DEVLOG.md` напоминание проверить `/members/login` до истечения срока (ориентир — начало октября 2026); если сертификат не продлится — потребуется отдельное решение (уточнить у Tilda-поддержки или ускорить переход на собственный кабинет).
2. **DDoS-Guard перед Tilda может выдать JS-challenge вместо контента** при трафике, который выглядит подозрительно (например, если Tilda сочтёт трафик с одного серверного IP аномальным). Обычный браузер проходит challenge сам, серверный reverse-proxy — нет. Явной защиты от этого в рамках текущей задачи не строим (сложно предугадать поведение чужой WAF); риск закрывается проверкой на этапе верификации ниже и последующим мониторингом.

## Проверка после деплоя

- `curl` напрямую на `/members/login` и `/members/register` через новый Caddy на проде — ожидается 200 и разметка Tilda Members (как при текущей прямой проверке через `176.57.67.189`).
- Живой тест в браузере: открыть кабинет на `dymova-english.ru`, залогиниться существующим аккаунтом, убедиться что сессия и куки работают на домене `dymova-english.ru`.
- Проверить, что остальной сайт (статика, `/api/lead`, обычные страницы) не задет переключением.
