## 2. Архитектура бэкенда

### 2.1 Технологии

```
Python 3.11 (Docker) / 3.13 (локально)
FastAPI + uvicorn (--proxy-headers за Caddy)
SQLite (WAL) — состояние диалогов и дедупликация
httpx — все внешние вызовы
pydantic-settings — конфиг из env
sentry-sdk — опционально
pytest + pytest-asyncio — 325 тестов
```

Зависимостей всего 8. Нет ORM, нет Redis, нет очередей, нет фронтенд-сборки — мини-аппы это
статические HTML/CSS/vanilla JS.

### 2.2 Слои и модули (`bot/app/`, 13 177 строк)

**Оценка:** архитектура для своего размера аккуратная — есть разделение на слои, точки входа
изолированы, singleton-геттеры (`get_llm()`, `get_kb()`, `get_store()`) позволяют подменять
зависимости в тестах. Код обильно откомментирован на русском с объяснением *почему* (следы
разбора реальных инцидентов). Это сильная сторона, ломать её не нужно.

**Главная слабость:** `ai_core._route()` — это лестница `if/elif` на 140 строк, где смешаны
маршрутизация, бизнес-правила, продажи и генерация текста. Каждый новый сценарий добавляет ещё
одну ветку. Именно здесь живут «преждевременные продажи» и «бот не понял потребность».

## 3. AI: как сейчас формируется ответ

### 3.1 Текущая LLM

`bot/app/config.py:31-44`:

```python
LLM_BASE_URL = "https://openrouter.ai/api/v1"
LLM_MODEL    = "meta-llama/llama-3.3-70b-instruct:free"   # ← бесплатная модель
LLM_TEMPERATURE = 0.4
LLM_MAX_TOKENS  = 700
LLM_TIMEOUT     = 40
LLM_TOTAL_BUDGET_SEC = 45
```

**Llama 3.3 70B (free tier OpenRouter)** — это ядро всего продукта. Проблемы:

| Критерий | Оценка | Комментарий |
|---|---|---|
| Естественность русского | ⚠️ средняя | Llama 3.3 на русском заметно «переводная», склонна к канцеляриту и англицизмам — в коде даже есть костыль `_mostly_russian()` (`llm.py:58`), отбрасывающий ответы, съехавшие в английский |
| Удержание контекста | ⚠️ | В LLM уходит только `history[-8:]` (`ai_core.py:228`), суммаризации нет |
| Следование бизнес-правилам | ⚠️ | Один большой промпт на 40 строк, без структурированных решений — модель сама решает, продавать или уточнять |
| Structured output | ❌ нет | JSON-режим/tool calling не используются нигде |
| Стоимость | ✅ 0 ₽ | free tier |
| Latency | ❌ плохая | free tier OpenRouter — очереди, отсюда `SLOW_NOTICE_SEC=12` и `REPLY_TIMEOUT_SEC=60` |
| Reliability | ❌ | free-модели регулярно отдают 429; каскад `LLM_FALLBACKS` по умолчанию **пуст** |

**Вывод:** бесплатная модель — это осознанная экономия, но именно она определяет потолок качества
диалога. Никакой промпт-инжиниринг не компенсирует модель, которая плохо чувствует русскую
разговорную интонацию. Это ключевое решение для Phase 2.

### 3.2 Пайплайн ответа (как есть)

```
message
  → dedup (processed_events в SQLite)
  → conversation_lock(platform, user_id)      ← сериализация, runtime.py:67
  → conv.add("user", text)
  → _capture_entities()                       ← regex: возраст, телефон, формат
  → intent.detect_intent()                    ← ЧИСТЫЙ regex по списку слов
  → registration gate                         ← если не зарегистрирован — анкета
  → _route()                                  ← лестница if/elif на 140 строк
       ├─ STAGE_LEAD    → lead_manager.step()
       ├─ STAGE_HANDOFF → шаблонный ответ
       ├─ OBJECTION     → sales.handle_objection() + LLM
       ├─ team_reply()  → карточки педагогов
       ├─ FACTUAL       → _consult(allow_web=True)
       ├─ WANT_SIGNUP   → lead_manager.start()
       ├─ GREETING      → жёсткий текст
       └─ иначе         → _consult()
  → _consult(): kb.search_scored() → [+ веб-поиск если score < 0.34] → LLM с системным промптом
  → проверка [UNKNOWN] / _UNCERTAIN_RE → при неуверенности handoff администратору
  → conv.add("assistant", reply) → store.save()
```

**Что здесь хорошо (сохранить!):**
- Сериализация диалога через per-user lock — устраняет race condition при быстрых сообщениях.
- Жёсткий дедлайн `REPLY_TIMEOUT_SEC` с честным фолбэком вместо молчания (`ai_core.py:339`).
- `_record_fallback()` сохраняет пару «вопрос → фолбэк», чтобы контекст не рвался.
- Индикатор «печатает» + промежуточный статус (`main.py:442-493`).
- Маркер `[UNKNOWN]` + защита от галлюцинаций с эскалацией администратору.
- Дедупликация апдейтов + корректное продвижение `offset` в long-polling (`main.py:684`).

**Что плохо:**
- **Intent — только regex** (`intent.py:93`). Список подстрок. «Ребёнок не хочет заниматься» → не
  совпадает ни с чем → `QUESTION` → общий `_consult`. Скрытая потребность не выявляется вообще.
- **Нет модели потребности.** `Conversation` знает возраст, формат и филиал. Не знает: цель,
  мотивацию, боль, предыдущий опыт, бюджет, срочность, кто принимает решение, возражения.
- **Продажа не заблокирована.** `sales.sales_nudge()` (`sales.py:106`) приклеивается к ответам
  безусловно, а системный промпт прямо требует: *«Каждый ответ мягко ведёт к следующему шагу:
  бесплатная диагностика или пробный урок»* (`sales.py:18`). Это ровно то, что запрещено в ТЗ.
- **Настроение — 25 подстрок** (`ai_core.py:49-64`). `_detect_mood()` вернёт `needs_empathy` на
  слово «ошиб», но не заметит «я в отчаянии, ребёнок ненавидит английский».
- **Нет AI-критика.** Ответ уходит пользователю как есть. Единственная постпроверка — регексп на
  «не знаю» и проверка «в основном русский».
- **Шаблоны.** Приветствие, handoff, отказ — жёсткие строки с эмодзи 🦊/😊. Повторный контакт
  всегда получает один и тот же текст. Запрещённые ТЗ конструкции присутствуют в коде дословно:
  «Отлично! 😊» (`lead_manager.py:25`), «Хороший вопрос!» (`ai_core.py:204`), «С радостью
  подскажу!» (`ai_core.py:506`).

### 3.3 Память

`memory.py`. Одна таблица `conversations(platform, user_id, payload JSON)`.

```python
@dataclass
class Conversation:
    stage, lead(Lead), history[20], transcript[1000],
    selected_course/branch/format, lead_step, handed_off, lead_submitted,
    last_user_intent/mood/topic, registered, utm, client_name, max_username
```

| Тип памяти | Есть? | Как |
|---|---|---|
| Short-term (текущий диалог) | ✅ | `history` — последние 20 сообщений, в LLM уходит 8 |
| Long-term (факты о человеке) | ⚠️ частично | Только `Lead` (ФИО/телефон/возраст) + курс/филиал/формат |
| Semantic (поиск по смыслу) | ❌ | Нет |
| Суммаризация длинных диалогов | ❌ | При >20 сообщений старое просто отбрасывается |

`is_returning()` (`memory.py:124`) — возвращающийся пользователь определяется как «есть факты И
прошло ≥12 часов», и на это выдаётся один и тот же текст: *«Привет! С возвращением! 🦊 Я помню ваш
прошлый диалог»* — при этом бот **не называет, что именно помнит**. ТЗ требует обратного:
«Мы с вами обсуждали занятия для Маши — хотите продолжить?».

**Риск производительности:** весь `Conversation` (включая `transcript` до 1000 сообщений)
сериализуется в JSON и переписывается целиком **на каждое сообщение** (`memory.save()`). Для
текущих объёмов приемлемо, при росте — узкое место.

### 3.4 База знаний (RAG)

`knowledge/kb.py` + `data.yaml`. Поиск — лексическое пересечение стеммированных токенов:

```python
score = len(query_tokens & doc_tokens) / len(query_tokens)
if doc.category in ("faq","courses","formats","team"): score += 0.1
```

Стеммер — самописное отсечение 40 суффиксов (`kb.py:30`). Порог «слабого совпадения» — `0.34`.

**Проблемы:**
- Нет синонимов и морфологической нормализации: «сколько это будет стоить» ≠ «цена».
- Нет эмбеддингов — вопрос «мой ребёнок боится говорить» не найдёт FAQ про языковой барьер.
- Бонус `+0.1` категориям — магическая константа без обоснования.
- В `ai_core.py:485-509` уже стоит **костыль на костыле**: три вложенных условия
  (`has_course_hint`, `recent_course_hint`, `conv.lead.age`) существуют только чтобы обойти то,
  что голое «сколько стоит?» находит нерелевантный документ. Комментарий на 14 строк объясняет
  историю трёх последовательных багфиксов. Это симптом слабого поиска, а не логики.

## 7. База данных

SQLite, файл `./data/bot.db`, режим WAL, `busy_timeout=5000`.

```sql
conversations(platform, user_id, payload TEXT, updated_at)  PRIMARY KEY (platform, user_id)
processed_events(platform, event_id, user_id, event_type, created_at)  PK (platform, event_id)
```

**Проблемы:**
1. **`processed_events` растёт бесконечно** — очистки старых записей нет нигде. На активном боте
   таблица будет расти линейно вечно.
2. **Дублирование механизма дедупликации.** `dedup.py` реализует ровно то же самое (отдельный
   SQLite-файл `dedup.db` + LRU в памяти) и **нигде не используется** — `main.py` ходит в
   `store.mark_event_seen()`. Мёртвый модуль на 87 строк.
3. **`_data` — неограниченный кэш в памяти.** `MemoryStore._data` держит все загруженные диалоги
   до конца жизни процесса, без вытеснения.
4. `all_conversations()` (`memory.py:203`) возвращает кэш, если он непустой, иначе читает всё из
   БД — для рассылок это означает загрузку всей базы в память.
5. Миграций схемы нет — только `CREATE TABLE IF NOT EXISTS`.

## 8. Безопасность

### Сделано правильно
- `hmac.compare_digest` для админ-токена (`main.py:147`) — защита от timing attack.
- Пустой `ADMIN_TOKEN` ⇒ все `/admin/*` отдают 401 (fail-closed).
- Личность в мини-аппах — **только** из подписанного initData; `MINIAPP_AUTH_REQUIRED=true`
  по умолчанию; проверка свежести `auth_date` (24 ч) — защита от replay.
- `/api/miniapp/profile` требует `verified=True` — ПДн не отдаются по открытому `?user_id=`.
- Rate limit на `/api/chat` (20 сообщений / 60 с) — защита LLM-квоты.
- Лимиты размера: текст 2000 символов, фото 8 МБ (`UploadFile.read(N+1)` — без OOM).
- Логи `httpx` подняты до WARNING — токены в URL не утекают в журнал.
- CORS ограничен списком доменов, только `POST`.
- Prompt injection: в системном промпте есть блок-защита (`sales.py:46-49`).

## 10. UX-проблемы

1. **Регистрация до первого содержательного ответа.** `REGISTRATION_REQUIRED=true` — человек,
   спросивший «сколько стоит?», получает анкету из 4 полей вместо ответа. Максимальный барьер
   на входе; ТЗ требует сначала понять человека.
2. **Тон.** Эмодзи в каждом втором сообщении, «Отлично!», «С радостью подскажу!», «Готово! ✅».
3. **Повторяемость.** Handoff-ответы ротируются между **двумя** вариантами (`ai_core.py:152`).
4. **Приветствие-простыня** для нового пользователя (`ai_core.py:534`).
5. **Заявка = анкета из 6 шагов** — ровно та «CRM-форма», которую ТЗ запрещает.
6. **Фото в Telegram-чате не разбирается**, хотя vision работает в мини-аппе.
7. **Возвращающийся пользователь** получает «я помню ваш диалог» без единой конкретной детали.

## 12. Где бот может зависнуть или потерять контекст

Проверено отдельно, потому что ТЗ выделяет это в приоритет.

**Защищено:**
- Общий дедлайн ответа + фолбэк (`ai_core.py:337`).
- Бюджет каскада LLM (`llm.py:241`) — иначе 3 попытки × N провайдеров × 40 с = минуты молчания.
- Любое исключение → человеческий текст, а не тишина (`ai_core.py:349`).
- Ошибка в фоновой задаче Telegram → фолбэк пользователю (`main.py:629`).
- `offset` в long-polling двигается всегда, даже для дубликатов (`main.py:684`) — иначе бот
  замирал навсегда после рестарта.
- Незавершённая заявка не теряется при постороннем вопросе (`ai_core.py:441`).
- Выход из анкеты работает на любом шаге (`lead_manager.py:233`).

**Остались дыры:**
1. `STAGE_HANDOFF` — почти поглощающее состояние. Выход только через `WANT_SIGNUP`
   (`ai_core.py:451`); на всё остальное — два чередующихся шаблона. Если бот один раз ошибочно
   передал диалог администратору, а тот не ответил, человек застревает.
2. `_process_update` (MAX) — **нет `_reply_while_alive` для ветки handoff/homework**, то есть
   на медленных путях MAX-пользователь не видит «печатает».
3. Ответ бота, отправленный после таймаута фолбэка, **не отменяется** — фоновая корутина
   `_handle_message_serialized` продолжает работу и запишет свой ответ в историю после фолбэка.
   Пользователь при этом видит только фолбэк → рассинхрон истории с тем, что человек прочитал.
4. При `stage == STAGE_DONE` (заявка отправлена) следующее сообщение уходит в общий `_consult`,
   но стадия не сбрасывается — состояние «залипает» в `done`.

**Общий вывод.** Это не «сырой бот» — это надёжно сделанный инструмент с хорошей инженерной
дисциплиной, у которого **слабое AI-ядро и шаблонный интерфейс**. Переписывать инфраструктуру не
нужно и вредно. Модернизация должна лечь поверх: новый мозг (Gateway + SMART + профиль + критик),
миграция MAX, и настоящий дизайн мини-аппов с уже существующим маскотом.

Приоритет исправлений:
1. 🔴 **MAX `platform-api2.max.ru`** — просроченная миграция, риск полного отказа канала.
2. 🔴 **AI-ядро** — Gateway, structured output, SMART, профиль, критик.
3. 🟠 **Mini Apps** — маскот вместо emoji, дизайн-система, микровзаимодействия.
4. 🟠 **Долг** — мёртвый `dedup.py`, TTL событий, rate limit на `/api/lead`, deeplink.
